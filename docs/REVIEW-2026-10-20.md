# Review, 2026-10-20: memory strategy, the expert index, MTP, and where the speed is

A factual audit of what this engine does with a GGUF that does not fit, what the
`<model>.krakenexperts.json` file is, what the MTP/nextn path can do today, and
how the measured numbers compare with other engines on the same card class.
Every number below is either **measured here** (command given) or **published**
(source and date given). Nothing is extrapolated without saying so.

Card: AMD Radeon RX 9070 XT, gfx1201, 16 GiB, 96 GiB host RAM, Windows.

---

## 1. What keeps a GGUF out of RAM and VRAM

Nothing here loads the file into memory. `Gguf` **mmaps** it and tensors stay
pointers into the mapping; every layer of strategy is about *which bytes are
copied where*, and about keeping the copy count small.

| Mechanism | Flag / switch | What it bounds | Where |
|---|---|---|---|
| mmap, no read-through load | always | nothing is copied at load; page cache holds the file | `src/gguf.cpp` |
| Dense-weight residency budget | `--weight-vram-mb` (0 = auto `free − reserve − 1 GiB`, negative = off) | device bytes for dense layers | `Model::set_weight_budget` |
| Layer streaming ring | automatic when a layer does not fit | one device ring, re-filled per layer | `src/model.cpp` |
| Two-buffer pinned staging | `KRK_WEIGHT_PREFETCH=1` (default) | read of layer L+1 overlaps compute of L | `Model::stage_layer` |
| Promotion of streamed layers | `KRK_WEIGHT_PROMOTE=1` (default) | keeps a layer resident when measured free VRAM allows | `Model::promote_layer` |
| Expert VRAM pool | `--expert-cache-mb` (auto, clamped after warm-up to `resident + max(0, free − floor)`) | routed experts on the device | `ExpertCache` |
| Expert WARM host tier | `--expert-warm-mb` | the corpus held in RAM; cold misses read the file | `ExpertCache` |
| Pinned WARM prefix | `--expert-pin-mb` | first N MiB of the tier as page-locked DMA source | `warm_fill` / `upload_pinned_batch` |
| Batched expert read | always | one read per layer per pass instead of one per expert (593 → 3400 MiB/s measured) | `prefetch_layer` |
| One-step staging | `KRK_ACTIVE_STAGE=1` | next routed expert of the same token promoted while the current one computes | `stage_next` |
| Batched-pass staging | `KRK_MOE_LOOKAHEAD=1` | union of a verify pass's experts promoted before row 0 (measured loss, off) | `stage_batch` |
| KV tiering | `--kv-hot-mb`, `--kv-warm-mb`, `--kv-cold-dir` | layer-granular KV slots across VRAM / host / disk | `kv_tier` |
| Ranked warm-up | `--expert-warmup`, `--expert-scan` | order in which the tiers fill | `warm_experts` |
| Router residency preference | `--router-resident P` | breaks near-ties toward what is already resident | `moe_ffn` |
| Host RAM policy | automatic | refuses staging past a reserve instead of swapping | `host_reserve_bytes` |

**Not present (gap):** KV-cache quantization. There is no `--kv int8` / k8v4
equivalent; the KV is f16 in a tiered cache. Strata uses int8 KV and a
32k-token resident window on the same card.

### Measured cost of the tiers (Nemotron-3.5-Lightning-30B-A3B NVFP4, 19.8 GiB file)

`-p "Explain…" -n 32 --ctx 1024 --greedy --expert-warmup 1`, same prompt twice,
only the WARM budget changed:

| WARM budget | VRAM resident | file reads during decode | promotions | decode |
|---|---|---|---|---|
| 6 GiB | 1221 slots (6.4 GiB) | **7879 MiB** (246 MiB/token) | 1374 | **12.6 tok/s** (79.7 ms/step) |
| 20 GiB (whole routed set, 15.8 GiB) | 1196 slots (6.4 GiB) | **0 MiB** | 1592 | **25.5 tok/s** (39.2 ms/step) |

The tier is worth **+102%** on this model, and the reason is one line: with a
WARM tier smaller than the routed set, every unreferenced expert is an NVMe read
inside the token. With the corpus in RAM the same step is pure VRAM traffic
(9.5 GB/s promotions, 551 µs/expert).

## 2. The `.krakenexperts.json` file

It is an **expert index**, not a loader index and not a cache: the per-layer
expert ranking measured by `--expert-scan`, which decides the **order** the
tiers fill.

* Written by `--expert-scan` (`write_expert_index`) to
  `<model_path>.krakenexperts.json`.
* Read at **warm-up** (`load_expert_index`), not at load.
* Validated before use: `kind`, `version`, `n_layer`, `n_expert`, `arch`; a
  mismatch is refused with the number that disagrees, because a ranking from
  another model is a well-formed file that orders the tiers by a distribution
  these weights do not have.
* **Path-derived**: renaming or moving the `.gguf` orphans the JSON, and a copy
  of the weights needs a copy of the index beside it. This is the usual reason
  it *looks* unused.

Measured today on the Nemotron file, with the index present:

```
expert warmup: using …/NVIDIA-Nemotron-3.5-Lightning-30B-A3B-NVFP4-noMTP.gguf.krakenexperts.json
               (512 positions, full-forward, 2944 ranked pairs)
expert warmup: ranked order, 1 rounds, 128 experts/layer deep;
               WARM 15758 MiB of 20000 MiB in 2944 slots (15758 MiB read),
               VRAM +1196 experts (6402 MiB, 1196 slots); 5510 ms
```

and on Tiel-Coder-35B-A3B the ranking is worth 16.6 → 23.9 tok/s at the same
pool and floor (recorded in `AGENTS.md`).

What it does **not** do: it does not skip file reads at random-access time and
it does not make `prefetch_layer` cheaper. It changes which experts are
resident, which is what the +44% on Tiel and the +102% above are made of.

## 3. MTP / nextn status

| Path | State | Evidence |
|---|---|---|
| In-model nextn block (`blk.<n>.nextn.*`) | works, probe + `--mtp-spec` | Tiel: 10/16 drafted tokens matched in `AGENTS.md` |
| **Sidecar block (`--mtp FILE`), new today** | works, probe + `--mtp-spec` | Nemotron: block 52 loaded out of the separate file (32 heads × 128, 128 experts × top-6, shared expert, 59 MiB resident); probe `MATCH` |
| Ungated expert bank in the block | works (loader + `mtp_ffn`) | Nemotron's block is up/down only |
| Per-layer `head_count_kv` array | works | Nemotron ships 53 entries |
| Sampling under `--mtp-spec` | **not supported** (greedy only) | engine warns and runs without the block |
| First-class `--mtp FILE` in the server | **not wired** | CLI only |
| Other head families (dflash / dspark / EAGLE) | `--draft` and `--draft-head` paths exist; dflash/dspark are separate drafters, EAGLE-3 loads from `tools/eagle_to_gguf.py` | `docs/AUDIT-*` |

Measured today with the sidecar (ctx 256–512, greedy, `--expert-warmup 0`):

```
nextn (MTP) block 52 loaded: 32 head(s) x 128, 128 experts x top-6 of 1856-wide FFN
                             + shared expert, eh_proj 5376x2688, 59.0 MiB resident
mtp probe: pos 0: draft 1044 "," (27168) | target 1044 "," (65184) | MATCH | 21.0 ms
mtp spec:  14 round(s), 6 of 28 proposals kept (21.4%), 1.14 token(s)/round
           | propose 254 ms | verify 936 ms | refeed 120 ms | block experts 128 ms
```

(Cold expert tiers: the block's 128-expert bank is paged by the same cache, so
21.4% is the drafter's greedy agreement, not a ceiling.)

### 4.3 The gap, stated plainly

| Axis | Us | Best comparable | Gap |
|---|---|---|---|
| MoE prefill, 30–66 GiB file on this card | 271 tok/s (Nemotron, 600-token prompt) | 800–958 tok/s (Strata, a **larger** model) | **~3.0–3.5×** |
| MoE decode, warm tiers | 25.5 tok/s (Nemotron) | 80.3 tok/s (Strata, spec 4 + MTP) / 84.3 (llama.cpp on 256 GB/s) | **~3.2×** |
| 8B dense decode | 92.3 tok/s (Qwen3-8B Q4_K_M) | 91.1–104.3 tok/s (llama.cpp HIP/Vulkan, same card) | **at parity** |
| Streaming, does not fit | 1.2–3.0 tok/s (27B Q4 at a 2–12 GiB ring) | no published equivalent | — |

Two facts worth keeping from this table:

* **The MoE path is where the gap is**, not the dense one. Dense decode on this
  card is already at llama.cpp's number; a 3B-active MoE is 3× behind.
* The 3B-active point matters: at ~4.5 bits/weight a token's expert traffic is
  ~1.7 GB, so the card's ~640 GB/s alone allows a **few hundred** tok/s. We
  spend 39.2 ms/step to move 8.5 GiB — about **22 GB/s effective**, i.e. 3–4% of
  the link. That is the headroom, and it is not bandwidth.

## 5. Investigate / fix, in the order the numbers argue for

| # | Item | Why (measured) | Lever | Cost |
|---|---|---|---|---|
| 1 | **MoE decode kernel efficiency** — 22 GB/s effective against ~640 | 39.2 ms/step for 1.7 GB of expert traffic | fusion, wider tiles, larger row batches, fewer launches per expert; profile with `--profile` **and** `kraken-bench --marginal` | M |
| 2 | **Prefill is 3× behind** (271 vs 800+) | 600-token prompt, 2 runs | batched expert GEMM (grouped), chunk size, `gemm_group` for prefill rows, expert prefetch per chunk | M |
| 3 | **Speculative decoding is not paying on MoE** | MTP accepts 21.4%, 1.14 tok/round; EAGLE head at 0% with a random head | acceptance-driven: draft-token count, min-p, sampling verifier, accept on the verify pass without a re-forward | M |
| 4 | **KV quantization** (absent) | Strata runs `--kv int8`/`k8v4` at 131k ctx on the same card | q8/q4 KV planes + attention kernels for them | L |
| 5 | **Expert traffic per token** (246 MiB/token at a 6 GiB WARM) | 12.6 vs 25.5 tok/s on the same model | size WARM to the routed set by default on MoE; warn when it is below `routed_bytes` | S |
| 6 | **Router residency preference is off by default** | 78.6% hot share already; +14.5% measured on Qwen3.8-35B-A3B | default `--router-resident 0.10` on MoE, after re-measuring the text | S |
| 7 | **`stage_batch` look-ahead** | prefill −8…−12%; decode ±0% (24.7/24.6, 25.5/25.9, 25.1/25.3 tok/s, promotions identical) | keep off -- promotions are already overlapped, so batching them earlier buys nothing | S |
| 7b | **Promotion traffic is the whole step** | 878 of 1214 decode ms in promotion: 8521 MiB at 9.5 GB/s, 1592 promotions / 31 steps; pool holds 18% of the routed set | raise residency (pool vs floor policy), raise `--router-resident`, or cut visits per token | M |
| 8 | **qwen4exp family** | 66 GiB Qwen3.8-Flash-Next refused by name (attn_gate, fused attn_qkv, ssm_*, QSA, PLE) | the exact model Strata runs at 810/80; per-stage port with the CPU oracle in `docs/AUDIT-qwen4exp-support.md` | XL |
| 9 | **Sidecar MTP in the server + sampling** | `--mtp FILE` is CLI-only; `--mtp-spec` is greedy-only | wire `cfg.mtp_path` in `main_server`, then the sampled verifier | S/M |
| 10 | **Multimodal (omni)** | no audio/vision path at all | separate project (llama.cpp-omni's shape: encoder + streaming scheduler) | XL |

### Claims this review does NOT support

* "We do 4× llama.cpp because of the expert cache." The cache is measured at
  **+102%** on this model (12.6 → 25.5 tok/s), and the remaining 3.2× gap to
  Strata's 80 tok/s is kernel/scheduling work that has not been done yet.
* "Strata is 3× faster" without qualifiers. It is 3× at *prefill and decode on
  a different (larger) model with spec 4 + MTP + int8 KV*; on dense 8B decode
  this engine is already at llama.cpp parity.
* Any Nemotron RDNA4 llama.cpp number: the 84.3 tok/s figure is **Strix Halo**
  (gfx1151, unified 256 GB/s), and the only RX 9070 XT Nemotron numbers found
  are site estimates (17 tok/s), not measurements.
