maclin: rr@10.0.0.12, Linux, 12 cores, 46 GiB RAM, /opt/rocm 7.17 (SDK 7.15),
AMD Radeon RX 6700 XT, gfx1031, 40 CU, 12.0 GiB VRAM. Models on nvme1n1p1

THIS IS THE FIRST TIME THE PRIMARY TARGET HAS EVER BEEN EXERCISED.
docs/HARDWARE.md names gfx1031 the primary target; until now every RDNA2 claim
in this repo was untested by construction.

THE BUILD NEVER WORKED ON LINUX
--------------------------------
build-hip on maclin failed with 4 errors that MSVC's transitive headers hid on
Windows, so the tree could not compile for its own primary target:

    include/krk/model.hpp     missing <cmath>      (std::tanh)
    src/backend_cpu.cpp       missing <cfloat>      (FLT_MAX)
    src/engine.cpp            missing <sys/stat.h>  (struct stat)
    src/hip/backend_hip.hip   missing <atomic>      (std::atomic fail counter)

Plus one defect this work introduced: attn_qtile_scores_bytes was defined AFTER
the kernel that calls it, which Linux/clang rejects (a dependent call to a later
declaration is not found by ADL) and the Windows toolchain accepted.

After those: build rc=0, 0 `error:` lines, and **kraken-tests 2154/2154 rc=0 on
gfx1031** — first time.

A CRASH ON THE PRIMARY TARGET
-----------------------------
Laguna-XS.2-IQ4_XS.gguf died with `Floating point exception (core dumped)`,
rc=136, after three lines of banner and before reading a single tensor. Located
with a RelWithDebInfo build + gdb: src/model.cpp:298,
`cfg_.n_head % cfg_.n_head_kv`, with n_head_kv == 0. It defaults to n_head, and
this file's head-count metadata yields zero, while the line above short-circuits
on `n_head_layer.empty()` and never validates. A second unguarded modulo at
line 559 (`% full_attention_interval`) had the same shape.

Both are now refusals, not divisions:

    kraken: head count is not a multiple of the KV head count     rc=1

THREE THINGS THIS SAYS, IN ORDER
---------------------------------
1. `warm_read` is 440 ms and everything else combined is ~270 ms. That is the
   ntfs3 path, not the engine: the same tree loads at 3.1 GB/s on Windows. Any
   RDNA2 throughput number measured on this mount is disk-bound and must not be
   read as a kernel result.
2. `gemm(simt)` runs at 11.4 GB/s against `gemm(gemv)`'s 132.5. That is the
   RDNA2 analogue of the staged-dequant problem on gfx12 (24 GB/s) and is the
   one genuine kernel finding on this card.
3. `download_f32` costs 1.40 ms of device but **122.65 ms of host** across 96
   calls -- 1.28 ms per blocking router-logit drain, worse per call than the
   0.151 ms barrier measured on the 9070 XT. The device-side routing plan is
   worth more on RDNA2 than on RDNA4, not less.
