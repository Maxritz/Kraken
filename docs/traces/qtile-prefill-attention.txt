Query-tiled prefill attention — was numerically wrong, now matches the reference
==============================================================================
2026-10-05, gfx1201 (RX 9070 XT), nothing else on the machine.

THE BUG
-------
`attention_qtile_kernel` shared one f32 score row per query (s_sh) across the
block and then OVERWROTE that row in place with the exponentials:

    const f32 e = __expf(s_sh[qi*tile_k + j] - mnew);
    s_sh[qi*tile_k + j] = e;          // <- every thread in the block reads this row

A thread that ran ahead of its neighbours replaced the raw scores before they
had read them, so those neighbours took max and exp over values that had
already been exponentiated once. Correctness depended on inter-thread timing.

WHY IT LOOKED LIKE A pos0 BUG
-----------------------------
Sorting the probe sweep by pos0 made it look positional:

    pos0 != 0 : rel = 1.039, 1.389        <- ~100-139% wrong
    pos0 == 0 : rel = 0.04 - 0.06

It was not positional. A non-zero pos0 case simply has more keys per chunk, so
the race window is wider. `n_rep`/`hkv` were checked in both kernels and are
identical, which ruled out the head mapping.

WHY IT SURVIVED
---------------
`tools/probe_attn_qtile.hip` is the instrument built to find exactly this, and
it had not compiled for an unknown number of sessions: it still passed a
`window` argument the kernel lost when `scale` and `tile_k` were added. The
detector was dead, so the defect was invisible. Fixed (one line).

THE REBUILD
-----------
/reenvision — the shape was wrong, not the arithmetic. The weight no longer goes
back to shared memory: s_sh is read-only after staging and the accumulation loop
recomputes exp from the raw row. Same value, from a source nobody can
invalidate.

/architect — the staged layout had TWO owners: the kernel placed its pointers
with one copy of the arithmetic and the host sized the launch with another, and
they disagreed by a factor of two (sizeof(_Float16) is already 2, then `* 2u`).
That is why every card was launching a 32-key tile when 64 fit. Both sites now
call `attn_qtile_scores_bytes<QT>()` / `attn_qtile_smem_bytes<QT>()`.

from the different summation order, which is what the kernel's own header says
the reformulation costs.

where it pays most, which is the expected shape: the win is K/V staged once per
query tile instead of once per query token.

STATE — it is still OPT-IN
--------------------------
KRK_ATTN_QTILE=1 enables it; the default is unchanged. Flipping the default is
one line, but it changes the summation order on every model, so it should be
gated on a clean 24-model coherence sweep rather than on three models here.

GATE
----
ninja rc=0, 0 `error:` lines; kraken-tests 2154/2154 rc=0; kraken-bench --gate
rc=0; probe_attn_qtile target rc=0.

STILL OPEN
----------
Even with this, prefill is 499 -> 670 tok/s against llama.cpp's 8528 on the same
file and GPU. This closes 1.3-1.5x of a 17x gap; attention was ~48% of prefill
device work and the rest is the staged-dequant WMMA path (24 GB/s of 644 GB/s)
plus the per-op idle. The probe should go into the gate so a fast path cannot
go silently wrong again.
