RX 9070 XT (gfx1201) — unblocking the Windows build, and the WMMA prefill GEMM
================================================================================

Host: Windows 11, C:/Users/rr/OneDrive/Desktop/kraken
GPU:  AMD Radeon RX 9070 XT, gfx1201, RDNA4, 64 CU, wave32
Tool: ROCm 10 runtime pack at G:/ROCM10RT-gfx1201 (HIP 7.16.26323, SDK
      7.16.26332), hipcc at lib/llvm/bin/clang++.exe

Everything in this file was measured on the 9070 XT. Earlier session numbers
came from maclin (6700 XT, gfx1031); the two are never mixed below.


1. THE BUILD WAS BROKEN, AND NOTHING ON THIS CARD HAD BEEN VERIFIED
--------------------------------------------------------------------------------
The first failure was not the compiler. The device bitcode was unreachable:

    clang++: error: cannot find ROCm device library; provide its path via
    '--rocm-path' or '--rocm-device-lib-path', or pass '-nogpulib'

ROCm 10 keeps the libraries at <rocm>/lib/llvm/amdgcn/bitcode. The compiler
searches <rocm>/amdgcn/bitcode, and only finds the ROCm 10 layout when
ROCM_PATH names the install root. G: is not the default prefix and the pack
is not on PATH, so every device compile failed.

CMakeLists.txt now derives the root from the HIP compiler CMake actually
resolved and passes --rocm-device-lib-path explicitly. Two details that
were needed to make it actually work:

  * The flag must be applied with add_compile_options/add_link_options, not
    target_compile_options(krk_hip ...). CMake compiles the executable
    targets' .cpp files with amdclang++ and an injected `-x hip`, so kraken,
    kraken-bench and kraken-oracle are device compiles too and they failed
    identically. Link options are needed as well: the device-link step
    resolves the same libraries.

  * A second tier was required on this host. At 17:16 on 2025-10-05 the
    directory G:/ROCM10RT-gfx1201/lib/llvm/amdgcn/bitcode was emptied while
    the tree above it stayed intact, and device compiles started failing
    again with the same message. The per-arch libraries are not pack
    specific, so CMake now falls back to a sibling pack sharing the
    compiler's product prefix (here ROCM10RT-gfx1031), which keeps the ROCm
    major version matched to the bitcode it has to load. Verified: the
    gfx1031 pack's oclc_isa_version_1201.bc compiles gfx1201 device code.

Build after the fix:

      rc=0, 0 lines matching 'error:'
    kraken-tests        rc=0, 2154/2154 checks passed
    kraken-bench --gate rc=0

4. WHERE THE TIME WENT: 6.5% OF THE TENSOR PEAK
--------------------------------------------------------------------------------
Qwen3-8B is 16.4 GFLOP/token. At 598.8 tok/s that is 9.8 TFLOP/s. The
9070 XT's fp16 tensor path is roughly 163 TFLOP/s, so the kernel was at
about 6% of what the silicon can do, while llama.cpp sits near 86%.

kraken-bench on the ffn gate/up GEMM [12288 x 4096], rows=55, four dtypes in
one process:

    q4_k    392.03 us   28.31 MB    72.2 GB/s   14.12 TFLOP/s
    f16     629.93 us  100.66 MB   159.8 GB/s    8.79 TFLOP/s
    q6_k   1160.49 us   41.29 MB    35.6 GB/s    4.77 TFLOP/s
    q8_0    380.48 us   53.48 MB   140.6 GB/s   14.55 TFLOP/s

The f16 row is the informative one. F16 weights change the staging byte
count by 3.6x and leave the WMMA instruction count untouched. Feeding the
same kernel more data made it SLOWER. A kernel that is neither compute-
bound nor dequant-bound, and that loses throughput to wider data, is bound
by the load path.


5. AN INSTRUMENT THAT WAS WRONG, AND WHY IT WAS REMOVED
--------------------------------------------------------------------------------
gemm_wmma_kernel already has a MODE parameter (1 = stage only, 2 = compute
only). Wiring it to an environment variable produced this, 3 reps
interleaved:

    full        354-398 us
    staging       5.9-6.6 us
    tensor        6.3-13.1 us

That is impossible and the arithmetic says why. MODE 2 skips staging, so
nothing inside the k_tiles loop writes xs or ws, every fragment load is
loop-invariant, and the compiler legally hoists the whole WMMA loop out.
MODE 2 timed one round instead of 32 and implied 1015 TFLOP/s — six times
the hardware peak. MODE 1 is not trustworthy either.

Both the instrument and the fragment-load vectorisation it accompanied were
measured flat-to-false and have been removed. The vectorised fragment loads
in particular changed nothing (13.56 vs 14.12 TFLOP/s) because -O3 was
already merging those scalar loads into vector loads. Neither is in the diff.


6. THE FIX: STAGE THE ACTIVATION TILE IN 128-BIT STORES
--------------------------------------------------------------------------------
The activation tile is the larger half of the staging traffic. The grid is
(12288/BN) * (rows/BM) = 192 column blocks, and every one of them re-reads
the same A rows, so activations move ~98 MB against ~28 MB of weights.

The old loop handed each thread 16 separate 2-byte elements per K tile.
It now hands each thread 8 consecutive halves, making each store 128 bits
wide. Same bytes, same values, same order — a store-width change, not a
reordering — so the tile is bit-identical. The vector path is guarded on
(n_in % 8 == 0, x 16-byte aligned, k_n % 8 == 0) and falls back to the
original scalar loop otherwise.

7. WHAT IS STILL MISSING
--------------------------------------------------------------------------------
Prefill moved 598.8 -> 828.7 tok/s. The gap to the reported llama.cpp 8528
tok/s on this card is still about 10x, so the WMMA GEMM is not the last
thing standing. What the measurements above say is left, in order:

  * No LDS double buffering. The kernel is stage -> sync -> WMMA -> sync per
    K tile, so the staging chain and the tensor work never overlap. LDS at
    BK=128 is 26 KB, and gfx1201 gives 64 KB per CU, so a second buffer fits
    but only at one resident block per CU. Whether that trade pays needs
    measuring, not assuming — see the MODE instrument problem in section 5
    for why the obvious way to measure it does not work.

  * A is re-read once per column block (192x for the gate/up shape). Raising
    BN, or scheduling blocks so a column of the grid keeps its A tile in L2,
    attacks the same traffic the fix above just halved.

  * The generic staging path (dequant_chunk_dev) is much weaker than the
    specialised Q4_K pipeline: q6_k costs 1160 us against q4_k's 392 us for
    similar byte counts. Qwen3-8B-Q4_K_M has Q6_K tensors (attn_v, ffn_down),
    so that gap is live on this model.

The kernel is still at roughly 24-30 TFLOP/s where the card can do ~163, so
there is a great deal of headroom above what is recorded here.

8. PREFILL GETS WORSE AS THE PROMPT GROWS, AND IT IS NOT THE GEMM
--------------------------------------------------------------------------------
Everything in section 6 was measured with --bench's 55-token prefill. That
batch is small enough to be latency-dominated, so it is not the number that
answers the question the whole exercise is about. Measuring the actual
scaling (greedy, --max-tokens 1, chunk=256, 2 reps each, very repeatable):

    21 tok    507.9 / 512.2 tok/s
    81 tok    829.0 / 824.5 tok/s
   321 tok    720.6 / 719.0 tok/s
   961 tok    395.7 / 394.7 tok/s

Throughput peaks near 81 tokens and then FALLS. A GEMM-bound kernel gets
faster as the batch grows; this one gets slower, so the bound is elsewhere.

Chunk size is not the cause -- 256/512/1024/2048 give 395.5/386.3/379.1/
375.1 tok/s at 961 tokens, flat to slightly worse.

The profile settles it. Two prompt lengths, same binary, NET device ms net
of the recorder floor:

    op            81 tok                    961 tok
    upload        399 calls   998.68 ms     399 calls  1061.24 ms
    gemm(wmma)    252 calls    60.40 ms    1008 calls   555.03 ms
    attention      36 calls    15.32 ms     144 calls  1855.97 ms

Two things fall out of that table.

upload does not scale with the prompt at all -- 399 calls and about one
second at both 81 and 961 tokens. It is the fixed weight load, showing up in
the window because the profile spans load as well as prefill. It is
host-bound (host 1053 ms vs device 999 ms) and carries 677 ms of GPU idle
waiting on it. It is a real cost and it is worth attacking, but it is not
per-token prefill work and it is not what makes long prompts slow.

attention is what makes long prompts slow. At 961 tokens it is 1856 ms of
the 2471 ms prefill -- 75% -- against 555 ms for every GEMM in the model
put together. 144 calls is 36 layers x 4 chunks of 256, at 12.9 ms each.

So the shape of the gap is not "kraken's GEMM is slow". It is:

  * at short prompt lengths the fixed host-bound weight upload dominates,
    and the section 6 staging fix is worth its 1.33x;
  * at long prompt lengths attention dominates at 75%, the GEMMs are a
    minority slice, and no amount of further GEMM work moves the headline.

This is where the remaining ~10x to the reported llama.cpp figure lives, and
it is a different problem from the one section 6 solved. The next thing to
measure is the attention kernel at prefill shapes, not the GEMM tile.

Caveat on these numbers: the profile reports 758 of 2068 ops at or below the
18.99 us recorder floor, so rows sitting on the floor are not individually
resolvable. The three rows quoted here (upload, gemm(wmma), attention) are
all far above the floor and their counts and byte totals are exact, but the
tail is bounded rather than measured.
