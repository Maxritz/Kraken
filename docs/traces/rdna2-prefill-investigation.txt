RDNA2 (gfx1031) prefill investigation — measured bottleneck ranking
================================================================================
Host: rr@10.0.0.12 (maclin). Card: RX 6700 XT, gfx1031, RDNA2, 40 CU, wave32,
12.0 GiB VRAM. No WMMA (both engines print this).
Model: Qwen3-8B-Q4_K_M.gguf (4.68 GiB), ntfs3 mount.
Reference: llama.cpp built natively for HIP on the same box and the same card
(build-hip1031, ROCm0: AMD Radeon RX 6700 XT). Same file, same card.

--------------------------------------------------------------------------------
1. Baseline, length-matched
--------------------------------------------------------------------------------
The earlier 4.2x figure compared a 55-token kraken prompt against llama.cpp's
pp512, which is not the same work. The prompt is now verified with kraken's own
--tokenize (361 tokens) and llama.cpp is run at exactly pp361.

  rep 1  kraken  361 tok in 1771.8 ms = 203.8    llama.cpp pp361 = 830.50

  kraken mean 201.0 tok/s vs llama.cpp 830.9 tok/s  ->  4.13x

--------------------------------------------------------------------------------
4. The two causes, both measured
--------------------------------------------------------------------------------
(a) The int8/DP4A rung is OFF BY DEFAULT ON EVERY CARD.

    backend_hip.hip:222
      const char *ie = std::getenv("KRK_GEMM_INT8");
      int8_gemm_ = ie && std::strcmp(ie, "0") != 0;

    The comment above it says it is lossy and "no default in this tree is
    allowed to be lossy". The dispatch trace confirms it never runs: base shows
    504 gemm(simt) and zero gemm(dp4a). Enabling it moved 432 of 504 GEMMs off
    the SIMT tile, and those 432 reach 10.33 TFLOP/s against the SIMT tile's
    3.78 — a 2.7x difference in kernel efficiency, not a marginal tuning win.

    The file also records the measured boundary (gemm_dp4a.hpp, kDp4aMinK=2048):
      SmolLM2-135M  K=576/1536   2827 -> 1641 tok/s   0.58x  LOSES
      Llama-3.2-1B  K=2048/8192  1120 -> 2060 tok/s   1.84x  wins
      Qwen3.5-9B    K=4096/12288  175.6 -> 198.7      1.13x  wins
    Qwen3-8B has K=4096/12288, the same regime as the 1.13x winner.

(b) Q6_K is excluded from DP4A, and those tensors are now the bottleneck.

    gemm_dp4a.hpp:563   constexpr bool kDp4aEnableQ6K = false;

    Qwen3-8B-Q4_K_M is a mixed quant. Per layer, from the file's own tensors:
      attn_q, attn_k, attn_o, ffn_gate, ffn_up   Q4_K (type 12)  -> dp4a OK
      attn_v, ffn_down                             Q6_K (type 14)  -> blocked

    With DP4A on, 72 of 504 GEMMs stay on SIMT and those 72 now cost 654 ms at
    1.08 TFLOP/s — the worst rate in the whole profile, and roughly half the
    arm's total time for one seventh of the GEMMs. The comment says the Q6_K
    kernel lost on register pressure (245 ms over 32 dispatches, 327 ms of GEMM
    against the fp16 tile's 256 ms) but "stays compiled and is covered by
    tools/gemm_i8k_verify.cpp so that a register budget can re-enable it".

--------------------------------------------------------------------------------
6. What is left, ranked
--------------------------------------------------------------------------------
1. Q6_K GEMMs: 72 calls, 654 ms at 1.08 TFLOP/s. Fixing the register budget
   behind kDp4aEnableQ6K is the single largest remaining item and the work is
   already scoped by the file and covered by tools/gemm_i8k_verify.cpp.
2. The SIMT tile at 3.78 TFLOP/s = 15% of the packed-fp16 ceiling. llama.cpp
   implies ~13.6 TFLOP/s on the same work (55% of packed). This is a tiling /
   occupancy problem in gemm.hpp, not an instruction-selection problem.
3. Attention: 438 -> 274 ms already captured by qtile; flash attention would
   attack the rest.
4. Whether KRK_GEMM_INT8 should become the default at all is a precision
   policy call, not a performance one. It is lossy by construction; it measured
   byte-identical on this model at this length, which is evidence and not proof.

Note on an earlier wrong turn: the hypothesis that this was an fp32-vs-fp16
precision problem was wrong. KRK_SIMT_USE_DOT2 excludes gfx12 on purpose, and
gemm.hpp documents the measurement behind it (gfx1201: 68 us scalar vs 195 us
packed for the same shape). On gfx1031 the packed form is already selected.

8. The int8 default checked against the models it could have broken
--------------------------------------------------------------------------------
Commit fc51584 made the int8 DP4A rung the default, on the argument that
dp4a_ok's kDp4aMinK=2048 keeps small-K models off it. That argument was
asserted, not measured, so it was measured: the two models on maclin that sit
either side of the gate.

  smolcode-coder-cpp-1.5b-q4_k_m   n_embd 1536  (every GEMM has n_in < 2048)
    KRK_GEMM_INT8=0   814.7 / 773.9 tok/s
    KRK_GEMM_INT8=1   811.2 / 806.2 tok/s
    generated text    IDENTICAL
    -> no regression. The gate holds: the rung never engages below K=2048.

  Llama-3.2-1B-Instruct-Q8_0       n_embd 2048  (n_in == 2048, at the gate)
    KRK_GEMM_INT8=0   1513.4 / 1442.2 tok/s
    KRK_GEMM_INT8=1   1992.2 / 1989.8 tok/s      1.32x
    generated text    IDENTICAL
    -> the win case reproduces on hardware, and with byte-identical output.

Instrument defect, recorded because it nearly made this look like a null
result: a helper counted "gemm(dp4a)" rows in a profile window with
KRK_PROFILE_STEPS=1, which is a DECODE step. Prefill GEMMs happen before the
decode steps, so the count was 0 for both models regardless of what the rung
did -- while Llama-3.2-1B was visibly 1.32x faster in the same run. A count of
zero from a window that cannot contain the thing being counted is a fact about
the window.

--------------------------------------------------------------------------------
9. Where the ceiling actually is on this card
--------------------------------------------------------------------------------
  RX 6700 XT, gfx1031, 40 CU, wave32, 12.0 GiB
    40 CU x 64 FP32 lanes x 2 FLOP x 2.41 GHz  = 12.3 TFLOP/s fp32
    v_dot2_f32_f16 (4 FLOP/instruction)        = 24.6 TFLOP/s packed fp16

  Qwen3-8B is 8.19e9 parameters, so 16.4 GFLOP/token of GEMM. At the packed
  fp16 ceiling that is 24.6e12 / 16.4e9 = 1,500 tok/s. A prefill figure in the
  thousands for an 8B model is not reachable on this card by any kernel; the
  number to beat is 1,500, and llama.cpp measures 831, i.e. 55% of it.

  Measured so far: 203.7 baseline -> 232.3 with the int8 default -> 265.5 with
  int8 and the query-tiled attention, i.e. 18% of the ceiling. The remaining
  3.13x to llama.cpp is 654 ms of Q6_K GEMMs running at 1.08 TFLOP/s plus the
  SIMT tile at 3.78 TFLOP/s (15% of the packed ceiling).
